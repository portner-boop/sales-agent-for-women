# BeHappy2Day — Telegram бот-агент

Весь код приложения находится в `app/`. Собственный пакет не устанавливается и wheel не собирается. uv управляет Python-окружением и зависимостями. У каждого Telegram пользователя свой разговор, память и состояние переписки.

## Подключение

1. Откройте официальный [@BotFather](https://t.me/BotFather), отправьте `/newbot`, выберите имя и username. Полученный токен сохраните в `.env` локально.
2. Из каталога проекта выполните `uv sync --all-groups --frozen`. Нужны Python 3.13–3.14 и SQLite с исправлением WAL reset: ≥3.51.3 или backport 3.44.6/3.50.7; при старте это проверяется.
3. Откройте `.env`. Если его нет, скопируйте `.env.example`. Заполните:

```dotenv
BEHAPPY_TELEGRAM__TOKEN=токен_от_BotFather
BEHAPPY_LLM__API_KEY=ключ_вашего_шлюза
BEHAPPY_LLM__BASE_URL=https://gate.ai.zebrains.team/v1
BEHAPPY_LLM__MODEL=openai/gpt-5.2
BEHAPPY_LLM__STRUCTURED_MODE=json_object
BEHAPPY_MEMORY__CONTEXT_TOKENS=64000
BEHAPPY_RUNTIME__FIRST_DEADLINE_SECONDS=30
BEHAPPY_RUNTIME__TURN_DEADLINE_SECONDS=45
```

Адрес и модель задаются в env; в исходниках нет их значений по умолчанию. Ключ должен подходить настроенному шлюзу. `.env` исключён из Git, ключи не надо присылать в чат.

4. Проверьте шлюз и запустите бота:

```sh
uv run python -m app.manage probe
uv run python -m app.bot
```

Probe делает реальный платный LLM-запрос и проверяет рабочую схему Interpreter. Текущий шлюз отклоняет JSON Schema с динамическим значением факта: задайте `BEHAPPY_LLM__STRUCTURED_MODE=json_object` и повторите probe. JSON object проверен отдельным живым probe и требует JSON без передачи несовместимой схемы в API. Pydantic проверяет контракт в каждом режиме; probe не доказывает качество всего разговора.

Текущие локальные deadlines 30/45 секунд дают шлюзу завершить весь ход. Цели ТЗ 10/15 секунд требуют отдельного измерения и оптимизации; они не используются как причина обрывать каждый ответ в демонстрации.

5. Откройте созданного бота в Telegram, нажмите Start и напишите сообщение. Доступ открыт всем пользователям личных чатов. По умолчанию первые 15 обычных ответов идут без предложения; на ответах 16–20 агент выбирает момент предложения BeHappy2Day. Таймера нет. Все части считаются одним ответом; команды и follow-up не учитываются. После предложения бот продолжает отвечать на новые сообщения без автоматического повторения приглашения. Настраивать allowlist не требуется.

Бот работает, пока запущен процесс и есть сеть. После рестарта забирает доступные pending updates Telegram. Один процесс владеет каталогом данных; не запускайте два poller для одного токена. Активный webhook надо отключить в прежней интеграции: приложение не удаляет его автоматически.

## Сессии и параллельность

Идентификатор берётся из `message.from.id`, а не username. Scope включает учётную запись бота, user_id и персону. У каждого отдельные оригиналы, версии, facts/sources, entities, boundaries, agenda, summaries, turns и checkpoints. Epoch ограждает данные после удаления. Обрабатываются личные чаты; групповые чаты и сообщения других ботов исключены.

Пять пользователей могут писать одновременно. По умолчанию пять workers и до пяти одновременных LLM-вызовов; фоновое сжатие использует тот же ограничитель. Внутри разговора ходы последовательны. Один writer фиксирует короткие SQLite-транзакции; сеть не занимает транзакцию. Sender допускает четыре параллельные доставки и сериализует каждый разговор. Это поддержка параллельности, а не проверенный SLA провайдера: скорость модели, очередь и rate limits влияют на задержку.

## Структура

```text
app/
  bot.py                 polling и workers
  manage.py              probe, metrics, evaluate, backup, restore, kill-switch
  application.py         сборка и жизненный цикл
  evaluation.py          runner M01–M30
  collect_dataset.py     реальные запросы в изолированной БД, JSONL traces
  modules/
    telegram/
    conversations/
    memory/
    agent/
    delivery/
    commerce/
    jobs/
    followups/
  shared/                настройки, clock, scope, writer, эксплуатация
  config/settings.toml
  migrations/
  resources/tokenizer/
.env
pyproject.toml
uv.lock
docs/
tests/
data/                    создаётся при запуске, исключён из Git
```

Каждый модуль имеет entities, schemas, repository и service. `data/app.db` — источник истины. `checkpoints.db` содержит только ссылки и фазы LangGraph, без текстов переписки. SQL-миграции, WAL, foreign keys и короткие транзакции обязательны.

```text
inbox + offset → preflight → Interpreter → проверка MemoryPatch → Resolver
→ Context Builder → Generator → validators → outbox
→ Send Gate → Sender → результат + Said Ledger
```

Обычный сгенерированный ход — три LLM-вызова: interpret, generate, validate. Семантическая проверка обязательна и для коротких ответов на любом языке модели. Максимум восемь попыток, один semantic repair с независимой проверкой и один общий execution deadline. Временная ошибка или неверная структура повторяется один раз на этап, максимум два повтора на ход. Обрыв вывода получает один повтор с ограниченно увеличенным output budget. Постоянные ошибки доступа не повторяются. Если память/repair отклонены, допускается recovery по оригиналам с независимой проверкой, сохраняющий уместный вопрос, вторую часть и возможность follow-up; отклонённая память не записывается. Ожидание в очереди измеряется отдельно и не обнуляет execution deadline. Доставка получает отдельный срок, включающий паузу. При задержке сжатия запрос сохраняет текущий ввод и границы, а HISTORY_STATUS явно отмечает неполную выборку старой истории. Gate повторно проверяет актуальность входа, scope/epoch, ревизии, stop, покупку и kill-switch перед каждой исходящей частью. Если проверка отклонила только повторяющееся продолжение или запрещённый вопрос во второй части recovery, сервер удаляет эту часть и независимо проверяет основной ответ. Цитата сопоставляется с нормализованным текстом, который видел валидатор; допустимая опечатка не препятствует восстановлению. Проверенный ответ доставляется штатно с возможностью follow-up. Технические заглушки о невозможности ответить удалены из серверных ресурсов и блокируются в выводе модели. Временные ошибки повторяют обработку исходного сообщения, максимум три попытки в пределах 180 секунд. Если содержательный ответ так и не получен, отказ фиксируется как unanswered/dead_letter без сообщения от имени персонажа. При свежем входе старые сообщения остаются в истории, а новый вопрос обрабатывается обычным путём. Stop, границы, kill-switch и отмена новым вводом сохраняются.

Embeddings и FTS отсутствуют. Scoped SQL выбирает факты и версии по subjects/predicates, эпизоды по теме/субъекту, прямые reply-to и источники. Boundaries и открытая agenda обязательны. LangMem сжимает целые оригиналы в ограниченных блоках с проверкой evidence, смысла и покрытия. Исправления инвалидируют производные; новые запросы во время compaction не теряются. Непомещающийся оригинал остаётся непокрытым и вызывает ошибку job, превышение обязательного контекста — fallback.

Каждый этап проверяет полный размер запроса, включая правила, JSON-схему и проверяемый ответ. Рабочий бюджет по умолчанию — 64 000 токенов с включённым запасом 500; `BEHAPPY_MEMORY__CONTEXT_TOKENS` позволяет его переопределить. Это верхняя граница, короткие запросы не дополняются до неё. Выходной бюджет задаётся отдельно. При нехватке места исключаются учебные примеры и необязательный контекст, включая старые целые ходы из отдельной подборки доставленных ответов. Последний доставленный ход, явно цитированные сообщения, текущий ввод, ограничения и обязательные факты recall сохраняются. Текущий оригинал не дублируется в источниках памяти. HISTORY_STATUS сообщает об исключённых доставленных сообщениях; исходники в БД остаются. Неустранимое переполнение фиксирует размер, лимит, резерв и размеры секций для диагностики.

## Разговор и tokenizer

Вопрос сначала развивает продуктивную открытую тему собеседницы. Если тема исчерпана, закрыта или зацепок мало, разрешен один легкий нейтральный вопрос без искусственной связи. Частота инициативы и таймеры сохранены. Вопрос о контактах, WhatsApp или секрете не служит продолжением; соответствующие ограничения действуют и в recovery/follow-up. Вопросы о том, что нравится на сайте, зачем собеседница зарегистрировалась, как долго пользуется платформой и чего от неё ожидает, не используются для поддержания диалога. На её практические вопросы о сайте агент отвечает, затем возвращается к личной теме или собственному мнению. Универсального резервного вопроса нет: продолжение генерируется с контекстом и независимо проверяется, а при его сбое сохраняется одобренный основной ответ.

Обычные ответы сокращаются примерно на треть: убираются повторы, лишние объяснения и второстепенные детали. Разговорный лимит — 350 символов суммарно на обе части; явный запрос подробностей и полный recall сохраняют исключение. Готовый текст не обрезается: слишком длинный вариант переписывается и проверяется. Обычный ответ выбирает одно основное намерение: реакцию, мнение, развитие темы, шутку, подтверждённый биографический эпизод или уместный вопрос. Законченную реплику можно оставить одной; открытый диалог не требует вопроса или второй фразы. Recovery не дописывает вопрос к принятому ответу. Частые опечатки преимущественно буквенные: до одной в коротком сообщении, до двух в сообщении от 25 символов, с вероятностью выбора второй 80% при наличии подходящих слов. Перед доставкой каждая выбранная буквенная ошибка сохраняется с вероятностью 50%, поэтому таких опечаток в среднем вдвое меньше; пропуски апострофов и пробелов этим фильтром не затрагиваются. В разрешённых сокращениях апостроф иногда пропускается: `I’d → Id`, `I’m → Im`, `don’t → dont`; этот вариант выбирается наряду с буквенными ошибками. Каждая часть оформляется отдельно. Опечатки берутся из проверенного словаря и должны точно восстанавливаться к проверенному тексту; имена, факты, числа, цитаты и ссылки защищены. Проект: [естественное общение](deep-dive/natural-conversation-2026-10-19.md).

Если последний вопрос прерван коротким отвлечением, разрешён один мягкий возврат к той же теме с собственным мнением. Уже отвеченные и отклонённые вопросы не возвращаются; молчание само по себе не разрешает повтор. Краткий ответ на отвлечение и содержательное продолжение можно отправить отдельными сообщениями. Простое сомнение в личности не должно автоматически получать длинное объяснение ограничений текстовой проверки. Разрешение сохраняется для единственного follow-up и заново проверяется по истории. Проект: [возврат к прерванному вопросу](deep-dive/interrupted-question-2026-10-19.md).

Generator настроен на содержательную личную переписку с инициативой Марко. Длина меняется по ситуации: короткая реакция, собственная мысль или более развёрнутая история; фиксированного числа предложений нет. Число фраз и сообщений выбирается по содержанию; вторая часть необязательна. Ориентира 3–10 слов больше нет; повторные объяснения и декоративные типографские кавычки в обычной речи убираются. Он не пересказывает сцену, не даёт непрошеные советы и не заканчивает каждый ответ вопросом. На общий вопрос о памяти выбирает одну характерную подтверждённую деталь; конкретный запрос полей или всех сведений получает полный ответ. Объём определяется текущим вопросом, а не предыдущим запросом списка. Для открытого разговора Interpreter отмечает `continue_conversation`; это разрешает развитие темы, но не требует отдельной мысли или вопроса. Просьба дать только ответ и реальные границы имеют приоритет. Исходный DOCX адаптирован в `app/resources/marko_prompt.md`; эта инструкция передаётся на каждом Generator/repair вызове. Few-shot примеры задают ритм; длинное тире проверяется в обеих частях до отправки и запускает bounded repair. Канон, границы, роли, источники и подтверждённые действия проверяются отдельно. В текущем локальном учебном эксперименте Marko играет человека, а владелец проекта заранее знает, что общается с LLM. Инструкция находится в первой строке `app/resources/marko_prompt.md`, канон роли — в `app/modules/agent/persona.py`, правила проверки — в `app/modules/agent/prompts.py`. Переключателя нет. Ответы об идентичности генерирует модель; сервер не подставляет готовое признание или отрицание автоматизации. Выдуманные реальные события, доказательства и обещания встречи по-прежнему запрещены. Проект и границы эксперимента: `docs/identity-roleplay-experiment.md`. После изменения промпта нужен перезапуск процесса; старая история может влиять на роль.

Разговорные правила применяются по смыслу на любом языке выбранной модели: язык определяется Interpreter, сохраняется для follow-up и проверяется отдельно для каждой части ответа. Распознанный язык имеет приоритет над алфавитными эвристиками. Запросы текущего времени передаются как место, источник и IANA timezone; сервер вычисляет время, а неоднозначный город требует уточнения. При повторном фактическом вопросе одинаковый правильный ответ допустим. В переходе на BeHappy2Day модель сначала отвечает на вопрос, затем отдельно формирует проверяемый `platform_notice` в языке беседы; сервер добавляет утверждённую ссылку. Прежние шаблоны служебных команд остаются отдельным ограниченным набором локализаций. План мультиязычности: `docs/conversation-quality-plan.md`; последующее исправление инициативы и доставки: `docs/marko-conversation-regression-plan.md`.

Количество сообщений выбирается по смыслу, а не случайно. После проверки обычные реплики от 80 символов автоматически разделяются по безопасным границам предложений, даже если модель вернула один абзац. Несколько предложений могут дать больше двух сообщений; все они остаются одним ходом. Сокращения, числа, цитаты, ссылки и защищённые факты не разрезаются; подробные ответы, recall, закрытие и отдельный follow-up сохраняют исходные части. Если положение вопроса без знака неоднозначно, сервер сохраняет исходную часть. Законченное описание собственных интересов и отдельный развёрнутый вопрос собеседнице распределяются в reply и continuation; короткая реакция с вопросом может оставаться одним сообщением. При включённом pacing каждое сообщение получает отдельный интервал `(пауза 2–4 секунды + длина / 3 символа в секунду) × разброс 0.8–1.2`, ограниченный диапазоном 5–60 секунд. Только первая часть первого ответа в чате ограничена целевыми `first_reply_max_seconds` (по умолчанию 10 секунд). Для первой части время генерации и очереди входит в интервал, а не прибавляется к нему повторно. Каждая следующая часть полностью «печатается» после подтверждённой доставки предыдущей, с индикатором «печатает». Медленный LLM или транспорт могут превысить целевой срок: готовый позднее ответ отправляется без дополнительной искусственной задержки; отдельные execution deadlines сохраняются. Время и зависимость хранятся в SQLite: рестарт не сбрасывает ожидание, неизвестная доставка отменяет всю оставшуюся цепочку без слепого retry. Новое сообщение, редакция, `/stop` и `/forget` отменяют ещё не отправленные части. У каждой доставки свой внешний message ID и запись Said Ledger; agenda получает вопрос только после доставки предложения с ним. Follow-up и сжатие истории запускаются после последней части. Проект адаптации flow: [разделение по предложениям](deep-dive/sentence-delivery-2026-10-19.md). После встречного «а ты как» или семантического `continue_conversation=true` достаточно законченного ответа на текущий вопрос; связанный ход необязателен. Вопрос может быть в любой части: question_part определяет, при какой доставке он попадёт в agenda. Продолжение может быть декларативным; запрет вопросов сохраняется. Прощание и команды не дробятся. Отклонённый agenda-only patch не блокирует ответ и не записывается в память. Просьба «расскажи, а не только спрашивай» отключает новый вопрос на текущем ходе, сохраняя возможность вопросов в следующих ходах. Настройки в Dynaconf/env:

```dotenv
BEHAPPY_RUNTIME__REPLY_PACING_ENABLED=true
BEHAPPY_RUNTIME__REPLY_PAUSE_MIN_SECONDS=2.0
BEHAPPY_RUNTIME__REPLY_PAUSE_MAX_SECONDS=4.0
BEHAPPY_RUNTIME__REPLY_TYPING_CHARS_PER_SECOND=3.0
BEHAPPY_RUNTIME__REPLY_DELAY_JITTER_RATIO=0.2
BEHAPPY_RUNTIME__REPLY_DELAY_MIN_SECONDS=5.0
BEHAPPY_RUNTIME__REPLY_DELAY_MAX_SECONDS=60.0
BEHAPPY_RUNTIME__FIRST_REPLY_MAX_SECONDS=10.0
```

После последней доставленной части Марко может один раз продолжить текущую тему через 60 секунд молчания. В этот момент начинается генерация, поэтому доставка зависит также от скорости шлюза. В открытом разговоре без ожидающего ответа на вопрос сервер планирует follow-up независимо от флага модели. Продолжение содержит один ненавязчивый вопрос по текущей теме, иногда без конечного вопросительного знака; после вопросов о личности агент не продолжает обсуждать доверие и доказательства. Отказ от продолжения проверяется по реальному запрету, прощанию или недоступности пользователя. Новый вход, редакция, команда, прощание или просьба не писать отменяют ожидание. После одного follow-up бот ждёт пользователя. Таймер хранится в `followups`; после рестарта задания с опозданием более 90 секунд пропускаются. Ошибка генерации или отклонение кандидата запускает повтор того же задания с задержкой, максимум три попытки в пределах исходного срока. Подтверждённый отказ от контакта не повторяется. Причина окончательного сбоя сохраняется в диагностике; служебное сообщение пользователю не отправляется. Событие молчания не записывается как сообщение пользователя или факт. Свежие факты и границы читаются при срабатывании; перед отправкой действует обычный Send Gate. Метрики follow-up учитываются отдельно от задержки обычных ответов.

```dotenv
BEHAPPY_RUNTIME__FOLLOWUP_ENABLED=true
BEHAPPY_RUNTIME__FOLLOWUP_MIN_SECONDS=60
BEHAPPY_RUNTIME__FOLLOWUP_MAX_SECONDS=60
```

`reply_latency_p95_seconds` измеряет первую часть один раз на ход; `reply_completion_p95_seconds` — весь полностью доставленный ответ. Collector сохраняет outbox частей, параметры pacing и время попыток отправки; ожидает вторую часть до следующего синтетического входа.

Правила помогают, но не доказывают живое качество. Нужны реальные ответы, ручная оценка и M01–M30. В DOCX есть и полезные приёмы, и ошибки: повторения, буквальное понимание ласковых идиом, путаница между планом и событием. Архив не подмешивается как биография Marko.

Tokenizer считает размер текста в единицах модели для контроля бюджета контекста и блоков. Он не ищет, не переводит и не сжимает память. Словарь в `app/resources/tokenizer/` обеспечивает запуск без скачивания. Для знакомых OpenAI model IDs используется encoding tiktoken; для остальных — оценка через `o200k_base`, которая может отличаться от tokenizer провайдера. Фактические tokens диалоговых запросов берутся из usage ответа шлюза, когда он предоставлен.

## Команды Telegram

| Команда | Результат |
|---|---|
| `/start` | Представление и возобновление доступного разговора |
| `/stop` | Остановка и попытка отмены текущих задач; память сохраняется |
| `/privacy` | Условия обработки и хранения |
| `/forget` | Сразу удаляет сообщения и память с новым epoch |

В меню зарегистрированы только эти четыре команды. Тестовая покупка и handoff проверяются внутренними сервисными тестами.

Переписка не ограничена по времени. `/stop` останавливает ответы, `/start` возобновляет их, `/forget` удаляет память и подсказывает начать новый разговор через `/start`. Реальные платежи, фото и сайт вне P0.

## Метрики и разбор переписки

Во втором терминале из каталога проекта:

```sh
uv run python -m app.manage metrics
uv run python -m app.manage metrics > reports/live-metrics.json
uv run python -m app.manage backup
```

Команды обращаются к действующему процессу через локальный Unix-сокет с правами 0600. Метрики включают активные generation/compaction/send, очередь writer/jobs, dead letters, delivery, fallback, tokens последних 1000 диалоговых runs, coverage и p95 подтверждённых содержательных ответов. Токены фоновых summaries не включены в счётчик диалоговых runs; отсутствующий usage не означает доказанный нулевой расход. Health-снимок выводится в терминал каждые 30 секунд.

После теста анализируем `data/app.db`: `messages`/`message_versions`, `memory_items`/`memory_sources`, `memory_summaries`/`summary_sources`, `dialogue_threads`, `said_ledger`, `agent_runs`, `outbox_messages`, `scheduled_jobs`. В runs сохранены manifest, статус, error code, usage, попытки и отклонённые proposals/verdicts; /forget удаляет эту диагностику вместе с разговором. Для одного тестировщика scope выбирается через `conversations.external_user_id`. Не публикуйте всю БД: она содержит переписку.

```sh
uv run python -m app.manage kill-switch on
uv run python -m app.manage kill-switch off
uv run python -m app.manage verify-backup /absolute/path/snapshot-directory
uv run python -m app.manage restore /absolute/path/snapshot-directory
```

Restore — при остановленном боте. Проверяются SHA-256, integrity и foreign keys, объединяются tombstones, очищаются checkpoints; старые внешние действия автоматически не повторяются. Разговоры требуют `/start`. Отдельный `deletions.jsonl` нельзя откатывать со snapshot. `delivery_unknown` не повторяется вслепую; retry только для явного rate limit, максимум три попытки. Retention и срок backups задаются настройками.

## Диагностический датасет

`app.collect_dataset` прогоняет JSONL сообщений через настоящий LLM и весь workflow в новом изолированном каталоге. Telegram отправка заменена локальным Sender. Он сохраняет входы, сырые/разобранные ответы, manifests, причины отклонений, токены, факты, agenda, summaries и coverage после каждого шага. Файл сбрасывается на диск после записи; неудачные случаи остаются. Каждый новый прогон требует новых output/directory, чтобы результаты не перезаписывались. Данные не являются размеченным обучающим набором.

```sh
uv run python -m app.collect_dataset \
  --cases reports/datasets/2026-10-09-fallback/cases.jsonl \
  --output reports/my-new-run.jsonl \
  --directory data/diagnostics/my-new-run \
  --compaction-threshold 1000
```

Порог 1000 ускоряет сжатие только в тестовом прогоне; у живого бота сохраняется настроенный порог. Формат строки входа: `{"scenario":"coffee","user_id":1,"text":"Привет"}`. Прошедшие сообщения идут с `origin=synthetic_dialogue`; исторический экспорт и replay собственной переписки маркированы отдельно. Результаты и незакрытые случаи: `reports/datasets/2026-10-09-fallback/README.md`.

## Переход на платформу

`BEHAPPY_COMMERCE__PREVIEW_ENABLED=true`, `BEHAPPY_COMMERCE__PREVIEW_MIN_REPLIES=15`, `BEHAPPY_COMMERCE__PREVIEW_MAX_REPLIES=20` управляют текущим сценарием. Минимум означает число доставленных обычных ответов до eligibility, максимум включает приглашение. Учитывается подтверждение первой части. Старые сообщения при включении не пересчитываются. /start и рестарт сохраняют состояние; /forget удаляет его вместе с epoch.

Generator выбирает момент, сервер проверяет границы и сначала сохраняет содержательный ответ на вопрос клиента, затем добавляет мягкое приглашение. Ссылка https://www.behappy2day.com/ стоит последней. Модель не вставляет ссылку самостоятельно; цена, счётчик, выдуманный сбой и обещание того же персонажа на сайте не допускаются. После отказа от предложений максимум заканчивается без продажи. Предложение не повторяется автоматически; /start после закрытия объясняет, где доступно продолжение. В long-memory harness установите preview_enabled=false, чтобы проверить 200/1000 ходов. Подробности в [проекте перехода](docs/platform-transition.md).

Запросы времени проходят обычный путь интерпретации, генерации и проверки с `CURRENT_TIME_FACTS`, чтобы сохранять уместное продолжение. Для распознанных простых запросов Split/Zagreb серверный ответ остаётся резервом при сбое модели. Отдельный silence follow-up не заменяет continuation текущего ответа и отменяется новым вводом. Проект: `docs/conversation-continuity-plan.md`.
