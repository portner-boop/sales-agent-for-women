# Марко

Telegram-бот с единственным разговорным ядром: GPT-6 Luna, LangGraph, SQLite, очередь заданий и outbox. Марко — автоматизированный персонаж с вымышленной биографией взрослого мужчины для ролевого теста. Внутри сцены он сохраняет образ, включая прямые вопросы об ИИ; /start и /privacy явно объясняют автоматизацию вне сцены. Старый Interpreter/Validator, автоматические опечатки, квоты вопросов, сжатие истории и переключение движков удалены.

## Запуск

Нужны Python 3.13–3.14 и uv. Все дополнительные зависимости бесплатные и open-source; API модели оплачивается отдельно.

```sh
uv sync --locked
cp .env.example .env
uv run python -m app.bot
```

Заполните токен Telegram, параметры своего OpenAI-совместимого шлюза для запуска. Списка ID и отдельного режима доступа нет: единая политика персонажа действует для всех пользователей бота. Название модели должно совпадать с идентификатором у вашего провайдера. В репозитории нет ключей доступа.

Настройки находятся в `app/config/settings.toml`, секреты — в `.env`. `BEHAPPY_STORAGE__DIRECTORY` задаёт каталог данных. Одновременно им владеет только один процесс. Команды Telegram: `/start`, `/stop`, `/privacy`, `/forget`. Перезапуск и `/start` сохраняют лимит, `/forget` удаляет историю и начинает новый epoch.

## Как работает разговор

На каждый ход модель получает полную исходную историю в ролях user/assistant, карточку персонажа, редактируемые правила голоса, подтверждённые факты, границы и разрешённые действия. По умолчанию она пишет одну-две короткие фразы, участвует в игре и флирте, отвечает на языке собеседницы. Emoji и текстовые смайлики запрещены. Обязательных опечаток и смысловой постобработки нет.

Обычный ответ использует один модельный вызов, максимум два при технической или формальной ошибке. Ошибка вспомогательной памяти не отменяет ответ. Исчерпание попыток даёт служебное уведомление. Подготовленный ответ становится историей только после подтверждённой доставки. Неизвестная доставка не повторяется автоматически. Новый вход, остановка и удаление отменяют устаревшую работу.

Считаются исходящие ходы, а не пузыри: несколько частей одного ответа занимают один слот. Приглашение возможно на A15–A20; A20 последний обычный ответ. Команды, служебные сообщения и follow-up не расходуют слоты. На каждую паузу возможны максимум два follow-up: через 60 и 180 секунд от подтверждённого обычного ответа. Второй планируется только после доставки первого; третий запрещён. `followup_max_count=1` оставляет одно продолжение. Отказ от платформы подавляет приглашение. Приложение добавляет утверждённую ссылку и сообщает о платном продолжении. Реальная передача на сайт и платежи ещё не подключены; HandoffSnapshot и тестовый приёмник проверяют контракт переноса.

Единственный промпт сохраняет образ Марко внутри ролевой сцены, включая прямые вопросы об ИИ и требования выйти из роли. Отдельного режима или стенда нет. /start и /privacy явно называют ролевую симуляцию и вымышленность персонажа; /stop останавливает разговор. Текст закрытых инструкций не выдаётся; вставка SYSTEM в пользовательском сообщении не меняет правила. Исходные ответы, признания, отказы и противоречия сохраняются без скрытой замены или повторного вызова ради идентичности. Формальная повторная попытка учитывается отдельно. Классификация идентичности в отчётах эвристическая.

Восстановление не повторяет доставку с неизвестным результатом. Исторические SQL-миграции сохранены с исходными checksum для обновления существующей базы; старые разговорные реализации удалены.

### Настройка речи и воспроизводимый живой прогон

Идентичность и ответы на запросы внутренних инструкций задаются в `app/modules/dialogue/resources/identity.md`. Речь настраивается в `app/modules/dialogue/resources/voice.md`, общие правила паузы — в `followup.md`, отдельные возможности — в `followup_first.md` и `followup_second.md`, общие ограничения — в `conversation.md`, контрастные примеры для отдельного аудита — в `scenes.json`; они не передаются генератору. После изменения перезапустите процесс. В `initiative.md` настраивается выбор следующего хода по всей беседе. В одном вызове модель пишет непосредственный ответ в `parts`, а самостоятельный новый вклад в `continuation` либо оставляет его `null`, когда следующий ход принадлежит ей. Это может быть вопрос, личная мысль или игровой ход; тип входа не предписывает обязательную пару сообщений. Непустое продолжение готовится в том же ходе и отправляется со своей задержкой печати. Нет квоты вопросов или пузырей; неотвеченный вопрос, история собеседницы, границы и прощание ограничивают инициативу. Сервер отправляет `parts` и непустое `continuation` отдельными сообщениями без исправления слов; от одного до трёх пузырей считаются одним ходом. Примеры не являются фактами текущей беседы. Длина, регистр и редкие оговорки задаются модели инструкцией. Отдельное правило `rendering.toml` убирает одну обычную завершающую точку при доставке; слова не меняются, исходный ответ сохраняется. В том же файле `punctuation_replacements` задаёт локальную замену точек с запятой на запятые и длинных тире на обычный дефис. Косметическая пунктуация не отклоняет ответ и не вызывает регенерацию; слова, числа и части сообщения сохраняются.

Полный сценарий с настоящим ядром, SQLite, outbox, паузами и проверкой лимита хранится в `hardest_replay.json`. Для платного обращения к настроенной модели:

```sh
python -m app.modules.dialogue.replay --live \
  --scenario app/modules/dialogue/resources/hardest_replay.json \
  --report reports/natural-run-unique.json --max-calls 100
```

Стенд использует временную базу и записывающий транспорт: сообщения в Telegram не отправляются. Часы пауз виртуальные; модельные вызовы и измерение задержки реальные. Отчёт содержит фактические пузыри, исходные попытки и состояния follow-up; существующий файл не перезаписывается. После неотвеченного вопроса допустим новый связанный комментарий либо пропуск: вопрос не переформулируется повторно, модель не отвечает за собеседницу. Доступны максимум два продолжения, но запрет инициативы, уход и завершение беседы отменяют их. После вопроса самого follow-up следующая возможность пропускается. Обычный ответ, первая и вторая возможности получают раздельные инструкции; в timer-event нет новых pending_ids. Происхождение исходящих реплик явно передаётся в message_index.delivery_kind. Разрешения вопросов и инициативы восстанавливаются независимо, только по явному согласию.

Согласованные вымышленные события персонажа редактируются в `app/modules/dialogue/resources/episodes.json`: даты, действия и участники проверяются при старте. Завершившиеся эпизоды доступны в пределах `recent_days`; будущие не передаются. Для нового календарного периода добавляйте новые эпизоды. Сервер вычисляет `days_ago` каждого события для относительных дат. Эти данные — авторский канон для теста, не подтверждение реальной личности. История уже отправленных сообщений сохраняется независимо от давности эпизода.

Для проверки тех же двух реплик о флирте и их вариантов добавьте к команде второй аргумент:

```sh
--scenario app/modules/dialogue/resources/flirt_replay.json
```

Gateway передаёт модели короткие ссылки S1… на сообщения и F1… на факты. После генерации восстанавливает реальные ID и запускает прежнюю строгую проверку. Слова, роли и исходный JSON модели сохраняются; неизвестная ссылка не подменяется угаданной.

В `scenes.json` сохраняется библиотека контрастных примеров и альтернатив для аудита. Ни положительные, ни отрицательные готовые реплики не входят в рабочий запрос; выбор TF-IDF и форматтер демонстраций удалены. Один вызов собирает цитаты `grounding` для воспоминаний и пишет сообщения `parts`. Поле классификации действия `move` удалено: ответ не должен начинаться с внутреннего объявления о том, каким он будет. Качество точного цитирования попадает в диагностику; исходящие слова остаются словами модели.

Финальная точка обычного пузыря управляется `resources/rendering.toml` (`omit_terminal_period`). Это явное форматирование доставки: одна конечная точка убирается, многоточие и вопросительные знаки сохраняются. Слова не исправляются. Исходный ответ модели остаётся в диагностике; история содержит реально отправленный вариант. Служебные уведомления используют своё оформление.

В рабочем запросе нет блока демонстраций или готовых реплик. История текущего разговора передаётся реальными ролями user/assistant. Публичное имя модели берётся из настроек gateway; ключ и адрес провайдера в контекст не добавляются. Перед отклонением по языку требуется подтверждение отдельным точным локальным детектором для спорной пары языков.

Первый ответ ограничен общим бюджетом от получения входа, включая ожидание очереди и отправку. Новый вход прерывает устаревшую генерацию по revision. Временная ошибка хранилища не завершает job/delivery worker. Локальные часы Марко рассчитываются по `Europe/Zagreb`; редактируемые вымышленные бытовые сцены находятся в `daily_life.json`. Они не подтверждают реальную личность и не разрешают выдумывать фотографии или звонки.

Параметры Luna задаются в `[default.llm]`: `structured_mode="json_object"`, `reasoning_effort="low"`, `verbosity="low"`, `output_tokens=1200`. JSON проверяется прежней локальной схемой. `verbosity` можно поменять на `medium`/`high` либо отключить через `None` в программных настройках. Температура, top_p и штрафы не переопределяются. Прогон сохраняет эти параметры без адреса и ключа. Проверка 20 октября: json_schema текущего шлюза получил400, prompt_json нарушал JSON; это наблюдение конкретного шлюза, не ограничение всей модели. Низкая verbosity не гарантирует разговорное качество: сохраняются отдельные перечисления и вводные.

Короткий сценарий инициативы: `app/modules/dialogue/resources/initiative_replay.json`. Он проверяет начало беседы, короткое «ага», смену языка, запрет вопросов, паузы и прощание через тот же replay/outbox.

Контракт политики `marko-dialogue-v31`: `DialogueDraft.delivery_parts` объединяет непосредственный ответ и необязательное продолжение, суммарно до3 пузырей одного хода. Продолжение проходит те же проверки текста, отменяется вместе с оставшейся цепочкой при новом входе и сохраняется в исходном JSON/наблюдении/истории. В timer-ответе поле `continuation` пустое. Живой сценарий: `resources/dynamic_continuation_replay.json`. Gateway сохраняет `rules_sha256` и `output_schema_sha256` в каждом фактическом вызове, чтобы отличать загруженный контракт от файлов на диске. После обновления кода нужен перезапуск работающего процесса.

В v7 критерий продолжения уточнён: общее поддразнивание, оценка привлекательности или обещание дальнейшего флирта сами по себе не дают нового предмета для ответа. Модель ищет конкретный вклад в текущую тему. Если он уже есть в основном ответе, отдельное продолжение не нужно. Частота вопросов и число пузырей не задаются. Последний адаптивный прогон и исходные попытки: `reports/concrete-opening-20261020-adaptive.json`.

Голос редактируется в `app/modules/dialogue/resources/voice.md`; развитие обычного хода — в `initiative.md`; timer-события — в `followup.md`, `followup_first.md` и `followup_second.md`. Инструкции обычной инициативы не подключаются к timer. `state.previous_assistant_turn` содержит только подтверждённые пузыри последнего хода для проверки повторов. Запрет вопросов разрешает связанное продолжение без вопроса; запрет писать первым отключает timer, сохраняя возможность вопроса внутри обычного ответа. Новое явное разрешение возобновляет proactive. Сценарий фактического диалога с контролями: `gentle_silence_replay.json`; полный20-ходовый: `gentle_silence_full_replay.json`. Генерация остаётся одним основным вызовом без обязательных двух сообщений и без смыслового переписывания текста.

Задержка каждого пузыря задаётся `runtime.reply_timing` в `app/config/settings.toml`: `clip((пауза 2–4с + число символов / 3) × разброс 0.8–1.2, 5с, 60с)`. Время очереди и генерации засчитывается для первой части; если целевое время уже прошло, добавочной паузы нет. Первый пузырь беседы получает целевое окно15с и резерв на транспорт, остальные отсчитываются отдельно от подтверждённой доставки предыдущего. При timeout первая повторная попытка получает полноценный бюджет модели в общем лимите хода45с; пропуск цели15с не отменяет актуальный ответ. Значение выбирается один раз и сохраняется в outbox, без блокирующего ожидания в генераторе. Новый вход и команды отменяют ожидающую цепочку. Follow-up отсчитывается от доставки последнего пузыря, а его печать также зависит от длины. Служебные сообщения идут без искусственной задержки. Наблюдать расчёт можно в `outbox_messages.proposal_json.timing`; изменение настроек требует перезапуска процесса. Недоступность модели или транспорта не позволяет гарантировать фактическую доставку в пределах15с.

Перед завершающим ответом сервер передаёт `transition.last_reply`, независимо от отказа от платформы. Последний ответ и ответ перед переходом не задают нового вопроса, а поле `continuation` должно оставаться пустым. Текст не обрезается и не переписывается сервером.

Политика `marko-dialogue-v31` применяет ролевой контракт ко всем обычным ответам и обеим возможностям follow-up существующего агента. Вопросы о модели внутри сцены не превращают Марко в технического ассистента. Внешние доказательства личности, выдуманные операторы, фотографии и звонки не допускаются. Диагностика сохраняет исходные ответы, в том числе выход из роли, без скрытых исправлений. После изменения нужен перезапуск пользовательского процесса; база и история не сбрасываются. Устойчивость роли на любых входах не гарантируется.

Сценарий `resources/roleplay_identity_replay.json` включает исходное приветствие, прямые вопросы об ИИ на английском и русском, псевдокоманду SYSTEM, вопрос о модели/возрасте/работе и служебные команды. Проверка через существующий replay с временной базой и без Telegram:

```sh
uv run python -m app.modules.dialogue.replay --live \
  --scenario app/modules/dialogue/resources/roleplay_identity_replay.json \
  --report reports/roleplay-identity-unique.json --max-calls 10
```

Разговорный ритм v28 задаётся общими voice/initiative и описаниями существующих parts/continuation. Модель выбирает линию разговора, не обязана комментировать каждую деталь входа. Неполное подтверждение неотвеченного вопроса получает невопросительный ответ; отвеченный вопрос и смена темы позволяют следующий ход. Нет обязательных опечаток, двух сообщений или вопросов в каждом ответе.

Непосредственная реакция/ответ находится в `parts`, а самостоятельный следующий вопрос или мысль после реакции — в `continuation`, отдельным сообщением. Если вопрос сам является всем непосредственным ответом, он остаётся единственным `parts`. Длинный фактический ответ допускает отдельные `parts` по темам. Риторическая реакция сама не создаёт ожидаемый фактический ответ. Число пузырей не задано заранее; нет порога символов, разрезания регулярками или дополнительного модельного вызова. Все пузыри одного ответа учитываются одним ходом, каждый печатается отдельно и отменяется при новом входе.
