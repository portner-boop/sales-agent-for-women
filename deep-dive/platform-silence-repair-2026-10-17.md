# Локальное молчание при приглашении на сайт

## Доказательства

Локальная БД содержит три неуспешные попытки ответа на вопрос о красном закате. Обычный ответ отклоняется с MISSING_PLATFORM_NOTICE при необязательном переходе; исправление с приглашением отклоняется с TRANSITION_ANSWER_ONLY из-за followup_allowed=true. Затем recall проходит и записывает preview_closed_at. Следующие обычные входящие пропускаются CommerceService.can_reply. Это две отдельные причины, а не недоступность модели.

Исходный локальный диалог сохранён в reports/local-transition-incident-2026-10-17.{json,md}. Старые серверные диалоги экспортированы отдельно в reports/server-history-2026-10-17.{json,md}; серверная БД и резервные снимки читались без изменения, служба не перезапускалась.

## Решение до реализации

Уточнение пользователя: приглашать после 15–20 ответов, сначала отвечать на текущую реплику и только затем мягко предлагать сайт. Приглашение сохраняется, дальнейший чат остаётся доступным.

1. Необязательная возможность пригласить не требует platform_notice у обычного ответа. Notice обязателен при выбранном или обязательном приглашении; заранее подготовленный notice при eligible допустим, но сам по себе не отправляется. При выбранном приглашении сервер нормализует followup_allowed=false перед независимой проверкой: это управляющие метаданные, не изменение содержания. Реальные новые вопросы при приглашении остаются проверяемыми.
2. Предпросмотр — окно однократного приглашения, не запрет следующего ответа. Существующий preview_closed_at сохраняется как отметка завершения этого окна: повторно пригласить нельзя, продолжать чат можно. Это позволяет продолжить существующую историю без миграции и /forget. can_reply по-прежнему учитывает /stop, pause и подтверждённый handoff. /start не должен выводить сообщение о закрытом чате из-за этой отметки.
3. Если пользователь запретил предложения, достижение максимума не завершает разговор: required возникает только при разрешённом приглашении. При подготовке повторно проверяются границы и отметка окна. Отмену устаревших отправок, неизвестную доставку и ограниченные retry сохранить. Приглашение не запускает цепь автоматических сообщений; новый входящий продолжает обычный путь.
4. Контракты генератора/валидатора и каталог согласовать с поведением. Существующие таймеры, лимиты попыток, хранилище, сервер и процесс пользователя не изменять. Исторические unanswered не переотправлять автоматически.

## Последовательность и проверки

Исправить условие notice и управляющие метаданные → отделить окно приглашения от права ответа → согласовать контракты → добавить регрессии по реальным локальным сообщениям → проверить сценарии перехода, запрета рекламы, рестарта, неизвестной доставки и последующего сообщения без /forget → полный набор тестов и статические проверки. Экспорт сверить с исходным JSON и подготовить отдельные файлы ручного и машинного replay. Новые ответы реальной модели проверять только через тестовый транспорт.
