# Серверная регрессия и проверка QMD, 2026-10-15

## Требования и границы

Сохранить настоящую проблемную переписку в отдельный Markdown для повторных тестов. Исходные реплики не исправлять. Разделить обнаруженные инциденты по реальным чатам: Ольга/Макс/дети/время, разговор про Египет и найденный в резервном снимке разговор Марии с unanswered. Не объявлять все перечисленные ранее баги доказанными одним экспортом. Историю, Xray и работающую версию сервера не менять.

Креды LLM обновлены; текущая модель OpenAI/gpt-6-luna, json_object. Python и QMD сравниваются на одной текущей модели, одинаковом каталоге и одинаковых входах. Старые измерения GPT-5.2 не используются как контроль новой модели.

## Данные и воспроизведение

Экспорт только выбранных диалогов: сообщения с порядком/временем/версией, подтверждённые отправки, статусы ходов, диагностические события. Не переносить токены, SSH-креды или сырые Telegram update. Артефакты с исходными личными данными — в игнорируемом reports, доступ к файлам только владельцу. Markdown сохраняет оригинальный текст и московские метки времени, показывает измеренную задержку и связи с инцидентами. Машиночитаемый JSON хранится рядом и служит источником повторов.

Сценарий replay использует последовательность пользовательских реплик из экспорта в новом изолированном приложении. Ответы генерируются заново; исходные ответы сохраняются только для сравнения. Серверные команды сброса истории не становятся пользовательскими сообщениями. Соседние сообщения пользователя до ответа объединяются в один вход с сохранением исходных sequence. Таким образом не воспроизводится исходная гонка доставки: её проверяют отдельные runtime-тесты. Короткие ответы могут ссылаться на исходную формулировку, поэтому это фиксированный сценарий, а не адаптивный человеческий диалог.

Оценщик проверяет факты и требования конкретного экспортированного чата, без старых синтетических Anna/Paris/nurse. Отдельно фиксируем: полноту ответа, память детей/питомца, повторы, вопросы подряд, время, границы, тон, фактические выдумки, ответы/пропуски, токены, обработку, выбор правил и fallback. Исходные серверные задержки и ускоренные часы replay не смешиваются.

## Сравнение подбора

Python: признаки Interpreter и серверное состояние → ID карточек → зависимости и обязательное ядро.
QMD BM25: тот же интерпретированный запрос → поиск по словам → проверенные ID → ядро/зависимости. Один запрос, лимит 1 секунда, полный резервный пакет.
Дополнительная изолированная проверка полного QMD: embeddings + гибридный поиск + reranking. Холодный запуск и прогретые запросы измеряются отдельно. Превышение секунды означает непригодность текущего варианта к ранее согласованному бюджету, даже если релевантность улучшится. Локальные модели не устанавливаются на сервер автоматически.

Решение о QMD требует одновременно приемлемых полноты правил, качества разговора, задержки и ресурсов. Перенос текстов в Markdown и выбор поисковика — отдельные решения. Если QMD не проходит, не переключать runtime и не убирать обязательные проверки. Если проходит — вынести дополнительные разговорные инструкции в версионированные карточки; контракты этапов хранить явно загружаемыми ресурсами, без случайного поиска обязательных инструкций. Детерминированные сроки, валидация схем, отмена, контроль прав и доставка остаются кодом. Фразы fallback рассматриваются отдельно: QMD возвращает правила, а не является резервным генератором ответа при отказе LLM.

## Последовательность

Проверка доступа → поиск и экспорт источников → Markdown и проверка совпадения с JSON → replay и метрики → оценка качества/скорости QMD → условные изменения архитектуры → релевантные регрессии и отчёт. Commit/push не выполнять. Выпуск на сервер не входит в эту итерацию до проверки решения на найденном сценарии.

## Найденное противоречие и необходимая правка

`language.reply_validation_instruction` по-прежнему навязывает одну деталь при общем recall, противореча SITUATION.RECALL. Это независимая от QMD ошибка предыдущего перехода на единый каталог. Первый replay остановлен до выбора архитектуры. Удаляем из языкового контракта разговорные нормы, которые уже принадлежат каталогу; сохраняем только языковую специфику. Тексты Interpreter/generator/validator/memory/summary/recovery/структурного ремонта/платформенных контрактов загружаются из app/policies/contracts/*.md через единый загрузчик. Их обязательная доставка на соответствующий этап не зависит от поиска QMD.

Проверенные детерминированные фразы photo/time/activity переносим из Python в app/policies/responses.json, сохраняя поведение для корректного сравнения. Их полное удаление не является следствием подключения QMD: поиск не генерирует ответ при отказе LLM. Решение о замене этих путей модельной генерацией рассматривается отдельно после результатов. Регулярные выражения, численные пределы, схемы, время и доставка остаются исполняемым кодом. Хеш реализации для эксперимента включает ресурсы .md/.json; после правки нужен новый прогон.

## Уточнение стенда

Ожидание outbox в replay должно учитывать зависимость второй части от доставки первой, как это делает рабочий DeliveryRepository. Иначе повторная генерация двух частей вызывает бесконечные нулевые сдвиги тестовых часов и ложную ошибку стенда. Исправление проверяется сценарием временного отказа Interpreter с последующей двухчастной доставкой. После него запускается отдельный verified-прогон; ранние прерванные результаты не объединяются с ним.

Для отделения поиска от случайности модели дополнительно используем одни и те же сохранённые выходы Interpreter: полный пакет, Python и BM25, по три повтора. Ручные ожидания наличия правил задаются только для девяти однозначных ситуаций из исходных диалогов; наличие карточки не считается доказательством качества ответа. Гибридный поиск измеряется отдельно от быстрого BM25.

## Исправление запроса BM25

QMD 2.8.3 соединяет слова лексического запроса через AND. Прежняя строка intent + все policy_topics систематически возвращает пустую выдачу на настоящих интерпретациях и фактически сравнивает Python с полным fallback. Этот результат сохраняется как диагностический baseline, но не считается проверкой работоспособного поиска.

Сохраняем один запрос без дополнительной LLM: выбираем первую тематическую метку Interpreter, которая существует среди conditions карточек. Для silence используем followup, для общей беседы — conversation. Несколько тем не объединяются через AND; обязательные ядро и серверные карточки по-прежнему добавляются независимо. Это честный ограниченный BM25-прототип, который зависит от качества Interpreter, как и Python. Проверяем реальные запросы contact/recall/time/verification/social на локальном индексе до нового полного live-прогона. В отчёте сохраняем фактическую поисковую строку.
