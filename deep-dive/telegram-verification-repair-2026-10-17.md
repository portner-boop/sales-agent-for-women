# Telegram: сетевой сбой и остановка разговора после проверки

## Подтверждённые причины

В приложенном traceback ChatActionSender._worker завершился с TelegramNetworkError, а его исключение не было извлечено. Затем лог содержит delivery_unknown и временные ошибки polling. Health продолжается, поэтому перезапуск процесса этим фрагментом не доказан. В локальной БД первая попытка доставки имеет неизвестный результат, после нового «?» доставлен новый ответ. Он содержит не запрошенный перечень ограничений фото/звонка, continuation=null и followup_allowed=false. Таймер продолжения не создавался. Новое сообщение Ольги впоследствии получило ответ: чат не заблокирован.

## Проект до реализации

1. Заменить сторонний ChatActionSender собственным небольшим TelegramTyping с тем же контекстным интерфейсом. Ответственность — только индикатор набора. Запрос ограничен по времени, временные ошибки повторяются с паузой, постоянный отказ прекращает индикатор, исключения фоновой задачи всегда извлекаются при выходе. Выход отменяет незавершённый запрос. Ошибка индикатора не прерывает тело контекста; отмена и исключение основной обработки сохраняются.
2. DurablePoller должен повторять безопасные операции чтения при сетевой ошибке, TimeoutError и TelegramRetryAfter, включая начальную проверку webhook. Пауза растёт с ограничением, RetryAfter учитывается. Успешный опрос сбрасывает задержку, offset остаётся прежним до успешного ingest. Постоянные ошибки и активный webhook не маскируются. Запись сообщения в Telegram остаётся отдельной: delivery_unknown не переотправлять автоматически, поскольку Bot API не даёт ключа идемпотентности.
3. В общем каталоге различить просьбу проверить без указанного метода и конкретную просьбу о фото/звонке. Для первой: коротко признать concern и уточнить желаемый способ, если вопросы допустимы. Не объявлять не запрошенные ограничения, не убеждать поверить, не придумывать доказательства или человеческую идентичность. При запрете вопросов — уместное содержательное продолжение без вопроса с возможным follow-up. Реальный ожидающий ответа вопрос не требует немедленного follow-up. Конкретный недоступный метод объяснять правдиво.
4. Историю, процесс пользователя и сервер не изменять. Проверить сбой typing при генерации, зависший запрос и отмену, сетевое восстановление polling, неизвестную доставку без повторов, дальнейший ответ и выбор инициативы на исходной реплике. Живой LLM проверять через временную БД и тестовый транспорт; его результат не является гарантией доступности Telegram.

Последовательность: TelegramTyping → безопасные повторы polling → каталог → регрессии → живой сценарий → профильные тесты и статические проверки.

## Дополнительное требование: заметные помарки

Пользователь просит пропуск буквы, перестановку соседних букв и пропущенный пробел. Существующее ограничение «сохранять все буквы» отменяется для таких явно разрешённых форм. Частота остаётся 40% подходящих доставленных ходов, не подряд и максимум одна помарка на ответ из одной или двух частей.

В style.json добавить проверяемый небольшой словарь бытовых слов/фраз и их читаемых ошибочных форм для нескольких языков. Это источник данных стиля, а не заготовки ответов. В STYLE_PLAN передавать допустимые формы только на запланированном ходе. Генератор предпочитает заметную помарку; если он вернул обычный текст, до независимой проверки сначала искать допустимую замену, затем использовать прежнюю пунктуационную правку. Не вставлять слово ради ошибки и не менять готовую помарку на вторую.

Детерминированное преобразование исключает имена сущностей и значения памяти, цитаты, URL/email, числа, отрицания и заглавные слова. Без подходящего места ответ сохраняется. Проверка evidence признаёт только пары из каталога либо прежние безопасные пунктуационные изменения. Изменённое содержание по-прежнему проверяет независимый валидатор. Проверить реальную доставку, неизменность защищённых фрагментов, один дефект на две части и отсутствие последовательных помарок.

## Дополнительный эпизод: комплимент и вечер

В журнале «I like talking with you too, Olga» отвечает на комплимент, а не на следующее сообщение про вечер. Последующее сообщение уже имеет подготовленный ответ и вопрос. Follow-up после комплимента был запущен: первая попытка повторяет вопрос о породе Макса, repair повторяет комплимент, recovery возвращает should_send=false. Уточнить правило о смене содержательного аспекта после комплимента: конкретное предпочтение или наблюдение вместо оценки клиентки и старого вопроса. Не обходить отказ генератора и проверку повторов принудительной отправкой. В живом replay проверять этот реальный эпизод отдельно.

## Дополнительное требование: инициатива сразу после ответа

В dialogue_plan обязательная содержательная вторая часть ошибочно зависит от questions_allowed. Разделить эти решения: continue_conversation задаёт наличие второй мысли, questions_allowed — только возможность запроса информации. Явный запрет вопросов допускает связанное мнение. Закрытие, служебная операция, repair и пересланный текст сохраняют существующие ограничения. Пауза между частями по длине сохраняется, таймер follow-up не заменяет вторую часть.

Interpreter должен выбирать продолжение для открытого социального обмена с новой личной деталью, взаимным интересом или приглашением поделиться. Не требовать заранее сформулированной второй реплики от этапа интерпретации: содержание выбирает генератор. Для подтверждения, завершения и просьбы об одном ответе оно не обязательно. Каталог задаёт один конкретный новый смысл в continuation: вопрос при разрешении или собственное предпочтение/наблюдение. Разговор о том, какой хороший разговор, не считается новым смыслом после комплимента. Не вводить обязательную вторую часть на каждом ходе, готовые фразы или новый LLM-запрос.

Проверки: две части при запрете вопросов без question_goal; отсутствие обязательного продолжения для закрытия/repair/служебного хода; запрет третьего подряд инициативного вопроса; живой сценарий комплимент → вечер → новая личная деталь → без вопросов → прощание, три повтора. Отдельно оценивать содержание, а не только количество сообщений.
